# Invited operator account setup

The invitation URL remains `/auth?mode=invite&ticket=…`. A read-only preview validates the signed tenant invitation before displaying the invited identity. The password is set only on explicit submission through `accept-invitation`; that server action enrols internal operators in version 1 of account setup. Public registration and customer portal access are unchanged.

Authenticated operators with incomplete setup enter `/onboarding`. Progress and Dexter exercise completion are server-controlled Auth `app_metadata`, checked by the account bootstrap and refreshed on completion. Existing accounts without the version marker are not enrolled. Each successful step is resumable after refresh, sign-in or OAuth return. Photos and connections may be deferred. Profile fields remain optional; continuing saves the values shown. Working hours and appearance use one save-and-continue action so a secondary action cannot discard entered choices. The three Dexter exercises must be completed before the server accepts final completion. This is an introduction, not an authorisation boundary for operational data.

Photo uploads, working hours, email, calendar and meeting-provider connections reuse the same APIs and private storage as Settings. Google Calendar provides Meet; Microsoft Calendar provides Teams. Email connections remain separate provider consent flows. Cancelling OAuth or a failed connection preserves setup, and provider state is read back rather than inferred from the redirect.

Department choices are descriptive profile metadata. They are validated against active departments in the operator's company. They **do not** change `cmp_Users_Departments`, roles, offices, permissions or other users: department assignments already participate in protected customs handoffs. Administrators retain control of access-bearing membership.

The development-only Profile action opens `/onboarding?preview=1`. The same UI reads the signed-in operator's profile, allows step navigation, and rehearses edits in memory. It never changes passwords, uploads images, saves profile/availability/theme changes or completes onboarding. Provider Connect actions still open the real, explicit consent flow. Preview is not available in production builds.

## Dexter and Watching for you exception

Invitation tickets, passwords, personal provider consent, onboarding progress and tutorial completion are deliberately unsupported as Dexter reads/writes or watch targets. They require the person at the account-setup surface, must not be completed on their behalf, and have no useful recurring watch event. The tutorial uses clearly labelled, deterministic practice content and never invokes a model, creates tasks, sends mail or updates operational records. Existing Dexter operational capabilities and watch lifecycles are unchanged. Profile department selections do not become operational department memberships or watch audiences.

The flow is Multideck-owned. Authentication stays on the standard identity and neutral light surface. Optional theme and accent choices are previewed locally, then saved to the operator's existing preference APIs. No tenant brand or browser theme controls the invitation surface.

## Design and verification

Mobbin research used the SavvyCal onboarding flow (https://mobbin.com/flows/7e290e37-db2f-47b4-9940-58263e3754d6) and Amie onboarding flow (https://mobbin.com/flows/fb0999bd-b493-4d74-aaf4-6dff3731562d), alongside the supplied Cal.com and ClickUp references. The result uses a fixed sheet, short conversational headings, staged decisions and progressive disclosure.

Appearance previews update the entire authenticated onboarding sheet through a temporary theme boundary and scoped accent variables. Preview mode does not save these choices. The password surface always retains the fixed light identity. The tiny Dexter samples use the app's painted bloom treatment without allocating a GPU renderer for every colour. Completion celebrates only after the server confirms success; preview completion never calls the save endpoint.

Motion uses directional step transitions, a filling progress track, small spring press responses, the app's copy/tick animation, its real dictation status pill, a finite simulated reasoning/answer sequence and an accent-tone confetti burst. Reduced motion keeps all information and actions available, immediately reveals tutorial replies and omits confetti. Example shipment rows and task approval remain explicitly illustrative.

Locally verified on 10 September 2026: production client build; 17 focused onboarding-state, invitation-signature, password-policy, recovery and theme-boundary checks; Chrome desktop and 390 × 844 mobile layouts; all three Dexter exercises, unsupported-prompt recovery, copy feedback, pasted prompt submission, reasoning disclosure reversals, real connected-provider readback, availability validation, department selection, theme/accent reversals, expanded colours, completion/confetti, saved-profile preservation after preview and reduced-motion fallbacks. The timezone picker shares the exact left and right bounds of the daily time inputs. The table, response and next action remain within the sheet, with long expanded reasoning scrolling inside the conversation area.

The account and accept-invitation functions were deployed to the development Supabase project. Anonymous/invalid bearer requests were denied; malformed invitation tickets were rejected. The frontend remains a local implementation. A fresh real invited account, real provider consent/return, actual photo upload and cross-project authenticated browser sessions have not been exercised end to end. The wider profile-media source-contract test has a pre-existing failure: it expects two setters to be adjacent, but HEAD already contains an intervening workspace-error reset. Its validation was not changed.

Persistence follow-up: profile updates require a returned company/user-scoped database row and confirmed Auth metadata. Saved theme/accent are loaded from the database, and both preference writes must return the selected values before completion. An explicitly empty department selection stays empty on reload. Real onboarding bypasses the development calendar preview store for availability reads/writes. Failed photo uploads prevent completion until retried, and appearance changes are locked while saving. Five additional handler-level tests cover persisted profile readback, empty departments, missing rows, Auth failure/retry, missing metadata and out-of-workspace department denial. These use an injected database adapter, not a real invited account.
