## Multideck and Tenant Theme Boundary

Multideck is the default theme and product identity for every new feature. Tenant branding is primarily a customer-facing override, not a global application theme. Do not apply tenant colours, logos, corner styles, or appearance variables across the application shell except for the explicit personal company-appearance choice below or a surface named in the tenant-brandable allowlist.

### Multideck-Owned Surfaces

The following must remain Multideck-branded:

- Application shell, navigation, Admin, Profile Settings, and internal operator workflows, except for the narrow opt-in company appearance treatment below.
- Authentication and security flows, including sign-in, invitations, verification, password resets, passkeys, access warnings, and security notifications.
- Permissions, audit, system-status, error, and other trust-critical product messaging.
- Dexter product chrome and any product-authored surface that has not been explicitly classified as tenant-brandable.

Tenant branding must never obscure that Multideck is the system handling authentication, access, security, or administrative actions.

### Personal Company Appearance Exception

When Admin Branding contains a saved company name and valid primary and secondary colours, signed-in internal operators may choose the company by name from Profile Settings > Customisation alongside the standard Multideck accent presets. An uploaded or imported logo is preferred; when none is available, use a restrained company-initials mark so a reviewed website import is still usable.

- The choice is personal, optional, and saved to the operator's profile. Multideck remains the default.
- The company palette may replace accent roles only. It must not replace neutral surfaces, light/dark preference, corner tokens, trust-critical colours, or the underlying Multideck component system.
- The expanded sidebar may show the bounded company logo (or company-initials fallback), a clear × separator, and the Multideck logo mark. Keep both identities visible and constrain the lockup so it cannot overlap notifications, collapse, or mobile-close controls.
- Hide the company option when Admin Branding is incomplete. If a previously selected company identity is removed, fall back safely to Multideck teal.
- Authentication, invitations, password resets, verification, access, security, permissions, audit, and Admin messaging remain Multideck-branded regardless of this choice.

### Tenant-Brandable Surfaces

Tenant branding may override Multideck only on explicitly customer-facing outputs:

- Shared contact cards. A deliberate per-card style override remains authoritative over the saved tenant brand.
- Operational customer email notifications for booking, shipment, and workspace updates.
- Every externally shared, unauthenticated customer web surface, including booking links, private meeting-management links, quote-response links, contact-card links, and future public web links generated by Multideck.

An external surface must never inherit the sending operator's personal light/dark preference, a recipient's saved Multideck preference, browser colour-scheme preference, or application theme storage. Its rendering precedence is: a deliberate record-level brand override where the product supports one; otherwise the configured tenant brand; otherwise the fixed Multideck public fallback of a white background, white surfaces, Multideck teal actions, dark readable text, and the standard Multideck identity. A tenant's saved dark appearance is company branding and may be honoured; an individual's dark preference is not.

The tenant brand contract may include the company display name and website; a logo with SVG preferred and PNG/JPEG supported; primary, secondary, background, surface, and text colours; light or dark appearance; rounded or sharp corners; and an operational-email sign-off. Saved tenant values become the default only for allowlisted outputs, with safe Multideck defaults when a value is missing or invalid.

Luna website import may suggest these values, including light/dark appearance, but it must create a reviewable draft and never save or publish branding automatically. Workspace administrators remain responsible for review and save under Admin Branding.

### Implementation Rule

For every new UI, notification, email, document, or shared output:

1. Classify it as `Multideck-owned` or explicitly `tenant-brandable` before styling it.
2. Use Multideck design tokens by default. Apply tenant values through a bounded semantic brand contract on allowlisted surfaces only; do not rewrite global tokens or CSS variables.
3. Preserve deliberate record-level overrides where the product supports them.
4. Isolate every external route from personal, stored, browser, and system appearance preferences. Do not add a visitor theme toggle to an externally shared surface.
5. Test the fixed white-and-Multideck-teal fallback and a realistic tenant brand, including logo transparency and placement, colour contrast, tenant light/dark appearance, and rounded/sharp corners where relevant.
6. Keep invitations, password resets, verification, access, and security communications on the Multideck template regardless of tenant settings.
